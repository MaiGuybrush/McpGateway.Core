MCP Tool 欄位命名標準化與
結構化 DTO 編譯期治理規畫

本工作規劃旨在解決跨業務系統（MES、EAP、Report、SPC、QC 等）欄位命名分歧與 Markdown 純文字回傳限制，將散落的「API 包裝器」升級為具備自主跨系統協同能力（Multi-Agent Collaboration）的企業級工具生態系。

核心轉型目標
消滅孤島，賦能協同

建立單層核心詞庫與強型別 DTO，讓 LLM 進行 Tool Chaining 時零猜測、零換算。

推動落地策略
低摩擦「鋪平道路」

不採強制編譯報錯（Hard Error），以 Roslyn 燈泡一鍵修復引導平滑過渡。

架構升級全景對比 Before vs. After

過去：各自為政 (Siloed)
  • 同一概念各自命名：ProductCode vs prod_id
  • 純文字 Markdown 回傳，無法二次排序與聚合運算
  • 跨工具鏈接（Tool Chaining）需浪費大量 Token 猜測
未來：統一契約 (Standardized)
  • Tier 1 詞彙統一名稱：標準 productId
  • 結構化不可變 DTO，自動暴露 JSON OutputSchema
  • Roslyn IDE 燈泡一鍵自動修復，開發零痛感
現況痛點與業務損失

為什麼必須進行標準化？現行四大阻礙

1. 命名歧異引發 LLM 幻覺與 Token 浪費 High Risk

相同概念在 Gateway A 叫 ProductCode、Gateway B 叫 prod_id、Gateway C 叫 materialNo。當 Agent 執行跨系統複合任務（如「查詢 WIP 異常並比對機台警報」）時，需耗費大量 Context 進行推論猜測，大幅提升對齊失敗率。

影響：多 Agent 協同（Multi-Agent）任務中斷與判斷失真
2. 純文字/Markdown 限制下游運算能力 Bottleneck

現有 Tool 以 Markdown 字串回傳資料，僅方便人類肉眼檢視，但 LLM 無法進行精確過濾、排序、聚合計算，下游自動化系統亦難以作為程式化 API 進行二次加工處理。

影響：無法支援進階資料統計與儀表板圖表自動生成
3. 缺乏欄位說明 (Description) 標準 Semantic Loss

開發者定義輸出物件時常遺漏中文語意註解，導致 MCP Tool 自動生成的 Output Schema 缺乏明確業務說明，LLM 在面對冷僻縮寫時經常誤解欄位用途。

影響：LLM 輸出語意對齊品質下降、使用者信任度降低
4. 歷史包袱導致「硬性阻斷」推行阻力過大 Adoption Risk

各部門資料庫與既有程式碼具有深厚歷史命名習慣。若在編譯期採取強制錯誤（Hard Error）阻斷，將使各單位專案無法順利建置，造成開發者強烈抗拒。

關鍵考量：必須提供「引導提示 + 一鍵修復」的柔性過渡手段
核心決策與技術架構

ADR-010 四大治理支柱 (4 Pillars)

完整涵蓋：型別契約、核心詞庫、編譯器治理、啟動防禦
1

強型別結構化 DTO

全面淘汰 Markdown 拼接字串，改以不可變 Record DTO 回傳。標註 UseStructuredContent = true，自動產生標準 JSON Schema（outputSchema）。

LLM 具備精確過濾與聚合能力
2

單層 Tier 1 詞彙治理

Tier 1 詞彙（Core Domain Vocabulary）：集中維護製造/半導體共通概念（productId, lotId, eqptId 等）及歷史別名。
子系統專屬詞彙（如 driftScore）直接寫在 DTO [Description]，不再另建本地詞庫（Issue #11）。

單一權威來源，避免雙層失同步
3

Roslyn 編譯器分析器

引入 McpGateway.Analyzers：
• MCP0010 (Warning)：偵測舊別名並建議標準詞
• MCP0011 (Warning)：提醒補齊 Description
• CodeFix：提供 IDE 燈泡一鍵自動修復！

開發即時提示，一秒完成修正
4

啟動期遞迴防禦

擴充 ToolStartupValidator（Rule #7），於 Gateway 啟動時反射掃描註冊 Tool 的 DTO 物件圖譜（支援巢狀與清單），若有遺漏 Description 輸出 Warning Log，不阻擋服務上線。

上線前最後防線，零當機風險
開發期 VS / VS Code 寫 Code
分析器輔助 Roslyn 警告 + 燈泡一鍵自動更名
啟動檢驗 StartupValidator 遞迴驗證 OutputSchema
Agent 賦能 跨 Gateway 零阻礙鏈接協同
落地效益與平滑過渡策略

「鋪平道路」治理哲學與業務預期效益

高 ROI、低推動阻力

為何不採「強制阻斷」？實踐以開發者體驗為核心

治理維度 強制阻斷模式 (Hard Error) ADR-010 鋪平道路模式 (Paved Road)
編譯與建置 違反規則即編譯失敗，中斷既有專案 Warning / Info 提示，不阻斷 Build
修復成本 工程師手動查詢規範與手動修改代碼 IDE 燈泡「一鍵修復」自動套用標準命名
業務特殊例外 無法彈性處理特殊專案欄位 專屬詞直寫 DTO [Description] 並支援 pragma 壓制
推動結果 業務單位強烈抗拒、推遲採用 自發性快速遵循，平滑完成標準化
1. 跨工具鏈接能力躍升 (Tool Chaining) Core Value

所有 Gateway 實體主鍵與通用狀態命名完全一致，Agent 可將 A 系統查出的 lotId / productId 零推理成本無縫傳遞至 B 系統。

2. 結構化二次運算與自動圖表化 Automation

前端 UI 與下游客製 Agent 能針對 DTO 欄位執行過濾、排序、分群運算，徹底告別純文字字串解析易破裂的窘境。

3. 零執行期額外負擔 (Zero Runtime Overhead) Performance

Roslyn 分析器僅於編譯期與 IDE 運作，設定為不進入產出 Assembly，對正式環境執行效能與二進位體積零影響。
